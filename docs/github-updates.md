# Обновления XAnty через GitHub

Канал обновлений настроен на публичный репозиторий [mur3r/XAnty](https://github.com/mur3r/XAnty). Пользователям не нужно вводить токены GitHub. Первая подключённая сборка — `2026.11.22.5`; более старые сборки с пустым адресом репозитория нужно один раз заменить вручную.

## Настройки канала

1. В `xgenius/update_config.json` указано `"repository": "mur3r/XAnty"`. Поле `asset` оставить `XAnty.exe`.
2. Собрать первую подключённую версию: `python tools/build_windows.py --onefile --dist-dir dist/release`.
3. Передать эту версию пользователям один раз. Уже выданные старые EXE без механизма обновления сами его получить не смогут.
4. Создать публичный GitHub Release с числовым тегом, совпадающим с `xgenius.__version__`, например `v2026.11.22.5`. Прикрепить именно `XAnty.exe`, собранный с `--onefile`.

Приложение обращается к `GET /repos/OWNER/REPOSITORY/releases/latest`. Черновики и предварительные релизы не предлагаются. Версии сравниваются численно, поэтому `.10` новее `.2`. Для проверки используется `digest` SHA-256 файла из API GitHub; релиз без него не устанавливается. См. [API релизов](https://docs.github.com/en/rest/releases/releases#get-the-latest-release) и [атрибуты файла релиза](https://docs.github.com/en/rest/releases/assets).

Для локальной проверки другого источника можно установить переменную `XANTY_UPDATE_REPOSITORY=OWNER/REPOSITORY`. Она предназначена для разработчика; в выпускаемом EXE адрес включается в сборку.

## Выпуск следующих версий

- Изменить `__version__` в `xgenius/__init__.py`, например на `2026.11.23.1`.
- Проверить тесты и создать тег `v2026.11.23.1`.
- Отправить тег в репозиторий. Workflow `.github/workflows/release.yml` выполнит тесты, подставит адрес текущего репозитория, соберёт однофайловый EXE и создаст черновик релиза с описанием.
- Проверить EXE и нажать **Publish release** на GitHub. После публикации подключённые приложения увидят обновление при запуске или очередной ежедневной проверке.

Workflow создаёт только приложение. Комплектные Chrome и ChromeDriver, аккаунты, cookies, рабочие папки и локальные настройки не публикуются. Для первого запуска на новом компьютере нужны отдельно предоставленные `Bro/chrome.exe` и `Drivers/chromedriver.exe`.

## Поведение у пользователя

При запуске и раз в сутки во время работы выполняется проверка. Внизу окна есть **Обновления** для ручной проверки. При новой версии появляется плашка с описанием и кнопкой **Обновить**. Загрузка идёт в фоне; после проверки размера, заголовка EXE и SHA-256 появляется **Установить и перезапустить**.

Установка доступна только в однофайловой Windows-сборке. Перед ней нужно закрыть профили и закончить переносы. Скрытый помощник PowerShell ждёт завершения XAnty, повторно проверяет SHA-256, сохраняет предыдущий EXE как `XAnty.exe.previous`, атомарно заменяет приложение и запускает его снова. При ошибке замены старый файл остаётся; при ошибке запуска помощник пытается восстановить резервную копию. Проверка успешного запуска новой версии не является автоматическим тестом её функциональности.

Обновляются только исполняемый файл и интерфейс внутри него. Аккаунты, сессии Chrome и выбранная рабочая папка не заменяются. Установку в защищённую от записи папку приложение отклонит с понятной ошибкой.

Файлы загрузки, последний результат установки и кэш проверки находятся в `%LOCALAPPDATA%\XAnty\updates`. Если процессу не удалось перезапуститься, можно вручную заменить EXE сохранённым `XAnty.exe.previous`. Переход из исходников или из onedir-сборки выполняется скачиванием однофайлового EXE со страницы релиза.

## Проверки

```powershell
python -m unittest discover -s tests -q
node tests/test_profile_ui.cjs
node --check xgenius/web/static/app.js
node --check xgenius/web/static/updates.js
python -m compileall -q xgenius tools
```

Автотесты используют изолированные файлы и ответы GitHub. Реальная публикация и замена запущенной пользовательской программы в тестах не выполняются. После предоставления репозитория нужно отдельно проверить живой релиз и обновление между двумя тестовыми сборками.
